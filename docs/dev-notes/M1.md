## Page speed in local development (11, 13, 18)
PERF1 stopped opcache from re-checking PHP files. The pages were still slow, so one Humas page was traced with strace:
about **400 file checks per request** on the Windows bind mount (about 6 ms each):
- ~165 from Blade: does the compiled view exist, is the source newer (`storage/framework/views` + `resources/views`);
- ~140 from the config: Laravel scans `config/` and the framework's own config folder on every request.

Fix, dev only:
- `docker/php/fpm.dev.conf` (new; `compose.yaml` mounts it as `php-fpm.d/zzz-sth-dev.conf`) sets the pool variables
  `APP_CONFIG_CACHE=/tmp/sth-cache/config.php`, `VIEW_COMPILED_PATH=/tmp/sth-cache/views`,
  `VIEW_CHECK_CACHE_TIMESTAMPS="false"` (quoted: a bare `false` is an empty value to php-fpm and stops it from starting).
- `config/view.php` (new): `check_cache_timestamps` from that variable, default `true` everywhere else.
- `docker/php/dev-cache.sh` (new; run by `start.bat` with `--force` and by `reload.bat`): empties the compiled views,
  rebuilds the config cache when `.env` or `config/` is newer than it, sends USR2 to php-fpm.
- `tests/TestCase::createApplication()` refuses to run when the config is cached or `APP_ENV` is not `testing`.

**Why pool `env[...]` and not compose `environment:` or `.env`:** pool variables reach the php-fpm workers only. The
command line (artisan, the test suite, the `queue` and `scheduler` containers) never sees `APP_CONFIG_CACHE`, so a test
run cannot load a cached config that says `APP_ENV=local` with the dev MySQL connection (`phpunit.xml` cannot override a
cached config, and `RefreshDatabase` would then wipe the dev database). The cache file also lives in `/tmp/sth-cache`,
never in `bootstrap/cache/`.

| measured | before | after |
|---|---|---|
| file calls per request (same Humas page) | ~400 | 139 |
| Humas pages | 480–720 ms | 260–430 ms |
| Kesiswaan pages | – | 215–450 ms |
| `/up` | – | ≈ 90 ms |

The lead's screenshots had shown about 1.1–1.2 s. Rule for developers (unchanged in spirit): after editing `.php`,
`.blade.php`, `config/*.php` or `.env` run `reload.bat`; never run `php artisan config:cache` / `optimize` by hand in
the repo. CSS and JS are not affected. PERF1's follow-up is still open and is still the real cure: move the repo onto a
Linux filesystem (the WSL2 distro has to be reinstalled by a human). File checks are then nearly free, so
`validate_timestamps` goes back to 1 and `reload.bat` is no longer needed; whether `fpm.dev.conf` can go as well has
not been tried.

## First use after a reload (added 2026-10-05, the lead asked about every role)
Measured for all seven roles + the public pages, every sidebar item, first visit and two more
(numbers per role: `catatan.md` §2). What was still slow after the config/view cache, and what was done:
- **The first request after `reload.bat` took 7.3 s** (login page) and the first login 5–6 s: USR2 empties opcache
  and php-fpm reads ~1,000 files from the Windows drive again. `App\Support\Dev\OpcacheWarmup` (+ the local-only
  routes `/_dev/opcache/save|warm` in `routes/dev.php`) remembers the project files php-fpm had compiled before the
  reload and compiles them again right after it; `dev-cache.sh` calls `save`, reloads, then in the background `/up`,
  three `warm` requests side by side, `/login`, `/`. `/tmp/sth-cache/warmed` appears when it is done (~28 s).
- **Each worker's realpath cache**: it is per php-fpm worker, empty in a new worker and expired after 600 s, so pages
  became slow again after a pause and whenever `pm = dynamic` started a worker. `fpm.dev.conf` now has
  `pm = static`, `pm.max_children = 3`; `php.dev.ini` has `realpath_cache_ttl = 604800`; the warm request resolves
  every remembered path under the exact string of Composer's class map.
- **Compiled views were all thrown away on every reload**: `dev-cache.sh` now deletes only the compiled views
  whose source is newer or gone (the compiled file ends with `/**PATH … ENDPATH**/`); `--force` deletes all.
- `composer dump-autoload -o` was run locally so the class map knows the M1 classes (vendor/ is not in git;
  `composer install` does the same because `optimize-autoloader` is on).
Result after a reload + warm-up: first visit of a menu 170–490 ms (one page 1,069 ms), later visits 149–538 ms,
login 744–928 ms (three requests + the password check; 1,852 ms for the very first login after the reload).
A single-file bind mount (`fpm.dev.conf`, `php.dev.ini`) keeps the OLD content after an edit until the container is
created again (`docker compose up -d --force-recreate app`, then `docker compose restart web`): a restart is not
enough. A bare `false` in a php-fpm `env[...]` line is an empty value and stops php-fpm from starting: quote it.
